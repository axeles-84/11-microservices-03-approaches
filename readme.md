# 🚀 Обоснование выбора инструментов для DevOps-инфраструктуры

В данном документе представлено обоснование выбора ключевых инструментов для обеспечения процессов разработки и сбора логов в микросервисной архитектуре.

---

## 🐙 Задача 1: Обеспечение разработки — GitLab CI/CD

**GitLab CI/CD** — это оптимальный выбор для крупной компании с микросервисной архитектурой, так как он представляет собой **единую платформу (All-in-One)**, которая объединяет Git-репозиторий, движок CI/CD и реестр контейнеров в одном месте.

### Ключевые причины выбора:

* 📦 **Единая экосистема без «зоопарка» инструментов.** 
  В отличие от Jenkins или TeamCity, которые требуют отдельного Git-сервера (GitHub, Bitbucket), GitLab предоставляет всё сразу: репозиторий, пайплайны, секреты, артефакты и container registry. Это радикально снижает операционную сложность.

* ✅ **Полное соответствие требованиям.** 
  GitLab CI/CD нативно поддерживает все пункты задания: от ручного запуска с параметрами (`when: manual` + переменные) до матричных сборок и собственных Docker-образов для job'ов.

* ♻️ **Гибкость и переиспользование.** 
  Механизмы `include` и `extends`, а также **CI/CD Components** позволяют создавать корпоративные шаблоны пайплайнов, что критично для десятков команд и сервисов. Вы один раз описываете стандарт сборки, и все команды его используют.

* 🔒 **Безопасность на уровне платформы.** 
  GitLab предоставляет встроенные механизмы работы с секретами (Masked/Protected variables), а также интеграцию с внешними хранилищами (HashiCorp Vault), что закрывает требование по безопасному хранению ключей.

* ☁️ **Гибридное развёртывание.** 
  Вы можете начать с облачного SaaS (gitlab.com), а при необходимости — развернуть полностью изолированный self-hosted инстанс со своими GitLab Runner'ами на собственных серверах или в Kubernetes, что даёт полный контроль над средой выполнения сборок.

## 📊 Задача 2: Сбор и анализ логов — EFK-стек

**EFK (Elasticsearch + Fluent Bit + Kibana)** — оптимальный выбор для компании с микросервисной архитектурой, где требуется **глубокий анализ и отладка** распределённых систем.

### Ключевые причины выбора:

* 📥 **Сбор из stdout без изменений в коде.** 
  Fluent Bit в режиме DaemonSet автоматически собирает логи со всех узлов Kubernetes, читая файлы контейнеров, куда пишется stdout/stderr. Приложениям не нужно ничего менять — они просто пишут в стандартный вывод.

* 🛡️ **Гарантированная доставка.** 
  Комбинация **файловой буферизации** в Fluent Bit и **Persistent Queues** в Logstash (если он используется как агрегатор) обеспечивает надёжность: даже при падении узла или недоступности Elasticsearch логи сохранятся на диске и будут доставлены позже.

* 🔍 **Мощнейший поиск.** 
  Elasticsearch индексирует каждое поле каждого лога. Разработчик может искать по тексту ошибки, по `trace_id`, по имени сервиса, использовать регулярные выражения и агрегации. Это критически важно для отладки микросервисов, где нужно найти причину сбоя в цепочке вызовов.

* 👥 **Гибкий доступ для разработчиков.** 
  В Kibana можно создать отдельное **пространство (Space)** для каждой команды и выдать роль только на чтение индексов этой команды. Разработчики получают доступ только к своим логам, не видя чужие.

* 🔗 **Сохранённые поиски и ссылки.** 
  Разработчик может настроить сложный поисковый запрос (например, «все ошибки 5xx за последний час»), **сохранить его** и отправить ссылку коллеге. Коллега откроет ту же выборку в один клик.

## 📈 Задача 3: Мониторинг — Prometheus + Grafana (+ VictoriaMetrics)

**Prometheus + Grafana** — оптимальный выбор для компании с микросервисной архитектурой, так как это решение является **де-факто стандартом** для мониторинга в Kubernetes и динамических средах.

### Ключевые причины выбора:

* 📦 **Сбор метрик со всех уровней «из коробки»:**
  * **Хосты:** `node-exporter` в режиме DaemonSet автоматически собирает CPU, RAM, диск и сеть с каждого узла.
  * **Сервисы/Контейнеры:** `cAdvisor` (встроен в kubelet) собирает метрики потребления ресурсов каждым контейнером (CPU, память, файловая система, сеть).
  * **Специфичные метрики:** `kube-state-metrics` отдаёт состояние объектов K8s (Deployment, Pod, ReplicaSet), а приложения могут отдавать свои метрики через стандартный `/metrics` endpoint.

* 📊 **Мощный UI с запросами и агрегацией.** 
  Grafana предоставляет единый интерфейс для визуализации. Язык **PromQL** позволяет делать сложные запросы: считать `rate()` ошибок, агрегировать `sum by (service, pod)`, вычислять перцентили (p95, p99) и строить алерты на основе этих выражений. Это критически важно для анализа RED-метрик (Rate, Errors, Duration) каждого микросервиса.

* 🛠️ **Гибкая настройка панелей.** 
  В Grafana можно создавать дашборды с панелями типов **Graph** (тренды), **Gauge** (проценты), **Stat** (текущие значения), **Table** и настраивать переменные для фильтрации по namespace, сервису или поду.

* 🚀 **Масштабирование под большие объемы.** 
  Хотя сам Prometheus не предназначен для вечного хранения (по умолчанию ~15 дней), для крупной компании это решается добавлением **VictoriaMetrics** в качестве удаленного хранилища (`remote_write`). VictoriaMetrics совместим с PromQL, обеспечивает высокую производительность и эффективное сжатие данных, что позволяет хранить метрики месяцами.
